## 2. 유형별 상세와 사례

공개 저장소 기준에 맞춰 사례는 최소 길이로만 인용했고, 사람 실명은 `○○○`로
가렸다. 반려동물 호칭이 들어간 사례는 아예 고르지 않았다.

### 유형 A — 헤딩 승격 오작동 (승격 헤딩 467개 중 304개, 65.1%)

승격 경로를 탄 문서는 58건뿐이고, 그중 **57건에 최소 1개의 잘못된 헤딩이
있다.** 승격된 헤딩 467개를 개별로 보면 304개(65.1%)가 제목이 아니라 문장
조각이다. 사유(중복 허용):

| 사유 | 건수 |
|---|---:|
| 직전 줄이 문장으로 안 끝남 (= 문장 한복판을 헤딩으로 잘랐다) | 258 |
| 조사로 끝남 (`~을`, `~는`) | 33 |
| 연결어미로 끝남 (`~해서`, `~지만`) | 32 |
| 3자 이하 | 30 |
| 접속어로 시작하거나 쉼표로 끝남 | 15 |

원인은 `is_heading_shaped()`가 "40자 이하 + `SENTENCE_ENDINGS`로 안 끝남"만
보기 때문이다. 하드랩된 본문의 거의 모든 줄이 이 조건을 통과한다.

**사례 A-1** — `naver_blog-africaamc-220358558555` (회수). 서명 한 문장이 두 줄로
하드랩돼 있는데, 앞줄이 헤딩으로 승격되고 뒷줄만 본문에 남았다.

```
>> ## '아프리카동물메디컬센터'
       입니다.
```

결과 청크 (전체가 이게 전부, 54자):

```
강아지 귀 청소하는 방법 > 오늘의 아프리카 주제는 바로 > '강아지 귀 청소하는 방법'
입니다.
```

본문이 `입니다.` 한 줄뿐인 청크가 6개, breadcrumb이 청크의 절반 이상인 청크가
99개 나온다. 임베딩에 들어가면 전부 제목 문자열의 중복 벡터다.

**사례 A-2** — `naver_blog-yoonsu3454-220932342135` (베럴독). 문장이 이어지는
한복판이 헤딩이 됐다.

```
   경계단계인 짖음을 무시했을 경우 강아지들은 방어적인 수단으로
>> ## 자신의 이빨을 드러내며 경고를 하게 됩니다
   그러다가 그것마져도 무시했을 경우 …
```

이 문서는 승격 20개가 전부 이상 판정이다. "방어적인 수단으로 / 자신의 이빨을
드러내며 경고를 하게 됩니다"라는 한 문장이 섹션 경계로 두 동강 났다.

**사례 A-3** — `naver_blog-africaamc-220540442077` (아프리카AMC). 승격 17개 중
13개가 이상. 헤딩으로 올라간 것 중에 `"` (따옴표 한 글자), `것`, `하는 행동교육`
같은 것이 섞여 있다. `heading_path`가 `['강아지교육 행동 교정 …', '"']`가 되고
그 섹션의 본문은 `입니다.` 한 줄이다.

### 유형 B — 헤딩 누락 / 헤딩 경로 자체가 안 잡힘 (771건, 93%)

네이버 블로그 두 소스는 사실상 전량이 하드랩으로 판정돼 char 폴백으로 간다.
이건 로직의 **오작동이 아니라 의도된 가드가 작동한 것**이고, 승격을 켰을 때
유형 A가 나오는 걸 보면 가드 판단은 옳다. 다만 결과적으로:

- 청크 5,389개 중 5,014개(93%)의 `heading_path`가 `[제목]` 하나뿐이다.
- "헤딩 우선 분할" 이라는 설계가 이 원자재에서는 실질적으로 작동하지 않는다.
  parent-child 리트리버를 붙일 근거로 남겨둔 `heading_path`도 값이 없다.
- 즉 829건을 넣는다는 것은 **문서 코퍼스의 93%를 순수 문자수 분할로 채운다**는
  뜻이다. 현행 코퍼스에서 이 경로가 차지하는 비중은 219청크 중 21개(9.6%)다.

### 유형 C — 하드랩 감지 실패 (32건)

`is_hard_wrapped()`는 `short_share >= 0.85` **그리고** `median <= 30`을 둘 다
요구한다. AND라서 한쪽만 걸린 문서가 승격 경로로 샌다. 유형 A의 원인 대부분이
여기다 (헤딩 경로 58건 중 32건이 이 경계선 문서다).

| 문서 | short_share | median | 승격 | 이상 |
|---|---:|---:|---:|---:|
| `naver_blog-yoonsu3454-220932342135` | 0.842 | 29 | 20 | 20 |
| `naver_blog-africaamc-220540442077` | 0.833 | 14 | 17 | 13 |
| `naver_blog-africaamc-220358558555` | 0.802 | 23 | 27 | 24 |

세 건 다 median은 임계를 여유 있게 통과하는데 short_share가 0.80~0.84로
0.85에 아깝게 못 미쳐 승격이 켜졌다. 임계 0.85의 근거는 "측정된 세 문서에서
89~100%"였는데, 829건 분포에서는 0.80~0.85 구간에 문서가 실제로 존재한다.

### 유형 D — 하드랩 결합으로 단어가 쪼개짐 (48~68회 / 36~46문서)

char 폴백의 `split_chars()`는 `\n`을 기준으로 조각을 나눈 뒤 **공백 하나로**
다시 붙인다. 원문이 단어 중간에서 줄바꿈된 자리에서는 단어 안에 공백이 들어간다.

```
원문 줄 5 : … 잠깐 조용해질 수는 있지만 강
원문 줄 6 : 아지 짖음의 원인이 그대로라면 …
결합 결과 : … 조용해질 수는 있지만 강 아지 짖음의 원인이 …
```

같은 방식으로 확인된 것: `생 후`(→생후), `환 경을`(→환경을), `말씀 드리자면`,
`머리 를`, `쪽 에`. 아프리카AMC 쪽에서는 서명이 `아프리카동물메디컬센` +
`터입니다`로 쪼개져 있는 문서가 31건이다.

**이 수치는 추정이다.** 사전이 없어서 "붙였을 때 코퍼스 전체에서 자주 나오는
토큰이 되고, 왼쪽 조각은 단독으로 거의 안 나온다"는 휴리스틱으로 셌다.
기준을 조이면 48회/36문서, 느슨하게 하면 68회/46문서다. 실제값은 이 사이
어딘가이고, 놓친 것도 있을 것이다. 문서 대비 5% 수준이라 빈도 자체는 낮다.

### 유형 E — 청크가 문장 중간에서 끊김

**여기는 수치를 하나로 못 쓴다.** 판정 기준에 따라 크게 갈린다.

- 엄격 기준(`ingest_documents.SENTENCE_ENDINGS`, 마침표 필수): 4,720 / 5,389 = **87.6%**
- 관대 기준(마침표 생략 허용, 한국어 종결어미 사전 확장): 3,369 / 5,389 = **62.5%**

네이버 필자들이 마침표를 자주 생략하기 때문에 엄격 기준은 확실히 과대계상이다.
관대 기준을 쓰고, 현행 코퍼스를 대조군으로 놓으면:

| 경로 | 현행 코퍼스 | 829 dry-run |
|---|---:|---:|
| `header+char_v3(auto_promoted)` | 5.6% (n=54) | **31.2%** (n=404) |
| `char_v3_fallback(hard_wrapped)` | 76.2% (n=21) | 65.1% (n=4,983) |
| `char_v3_fallback` | 24.1% (n=29) | 0% (n=2) |
| 한국어 문서 전체 (PDF 제외) | **25.0%** (n=104) | **62.5%** (n=5,389) |

읽는 법:

- 하드랩 폴백 경로의 절단률(65%)은 **새로 생긴 결함이 아니다.** 현행 코퍼스에도
  같은 경로가 21청크 들어와 있고 그쪽이 오히려 76%다. 문장부호가 없는 본문에서
  문자수로 자르면 나오는 당연한 결과다. 달라지는 건 비중이다 — 9.6% → 92.5%.
- 반면 헤딩 경로는 5.6% → 31.2%로 **5.6배 나빠진다.** 이건 새 결함이다.
  현행 54청크는 사람이 헤딩을 확인한 문서에서 나왔고, 829건의 404청크는
  유형 A의 잘못된 헤딩에서 나온다.
- PDF 경로(115청크)는 영문이라 한국어 종결어미 판정이 통하지 않아 대조군에서
  제외했다. 위 표의 "현행 25.0%"는 그 115개를 뺀 값이다.

관대 기준으로도 잘린 실제 예 (끝부분만):

```
… 원하는 것을 얻기 위한 요구성 짖음, 보호자가 사라졌을 때 나타나는 불안성 짖음,|
… 이후 성공 경험이 충분히 쌓였을 때 거리를 조금씩 줄여나갑니다. 3.|
… 이때 주변의 물건뿐 아니라 보호자의 손이나 발까지 깨물면서 … 2. 놀이라는 것을 잘못 배운 경우|
```

열거 중간, 번호 항목 직후에서 끊긴다.

### 유형 F — 청크 길이

- **480자 초과: 0개.** `split_chars(reserved=...)`가 breadcrumb 길이를 미리
  빼두는 처리가 829건에서도 정확히 지켜졌다. 길이 상한은 문제없다.
- **150자 미만: 350개(6.5%).** 최소 31자. 경로별로 성격이 다르다.
  - char 폴백: 190 / 4,983 = 3.8% — 대부분 문서 꼬리 조각이다. 정상 범위.

### 유형 G — 보일러플레이트·공유 접두사 (청크 1,793개, 33.3%)

`clean()`이 놓치는 반복 문자열이 소스마다 뚜렷하게 있다. 최근 Q&A 소스에서
breadcrumb이 임베딩을 오염시킨 것과 같은 구조다.

**사례 G-1 — 네이버 카테고리 + 작성자 + 작성일시 (124~281청크).** 크롤러가
본문 앞에 붙인 메타 줄이 그대로 살아남아 도입 청크의 첫 문장이 된다.

```
강아지 훈련을 통한 행동교정!두가지 교육방법
훈련/케어/질병 ○○○ 애견훈련소장 2018. 12. 14. 23:50 … ○○○입니다 어제는 눈이 …
```

- `2018. 7. 26. 22:39` 형태 타임스탬프가 든 청크 124개.
  `clean()`의 `DATE_LINE`은 `^\d{1,2}월 \d{1,2},? ?\d{0,4}$`만 잡는다. 네이버 형식과 안 맞는다.
- 카테고리/시리즈 라벨(`훈련/케어/질병`, `강아지 공부`, `반려견 행동교정`) 281청크.
- 작성자 서명(`…애견훈련소장`) 91청크. `SIGNATURE_SUBSTRINGS`에 `애견훈련사`는
  있는데 `애견훈련소장`은 없다.
- **도입 청크(#0)의 33.4%(277/829)가 이 셋 중 하나로 시작한다.**

**사례 G-2 — 링크 유도 문구.** `아래링크는` 167청크, `바로가기`/`바로 가기`
119청크. 아프리카AMC는 `▼ 아프리카 동물병원 홈페이지 바로가기 ▼`가 본문
전체인 청크까지 만든다.

```
강아지 산책 : 강아지 신발 필요할까?
▼ 아프리카 동물병원 홈페이지 바로가기 ▼
```

`PROMO_SUBSTRINGS`에 `오시는 길`, `진료시간`은 있는데 `바로가기`가 없다.

**사례 G-3 — 하드랩으로 쪼개져서 필터를 빠져나간 서명.** 아프리카AMC 문서
189건 중 **80건(42%)에서 `입니다.` 한 줄이 단독으로 살아남는다.**

### 유형 H — 인코딩·특수문자: 문제 없음

- U+FFFD(대체 문자) 0, lone surrogate 0, 제어문자 0, HTML 엔티티 0,
  zero-width 0, private-use 0. **829건 전부 정상 UTF-8이다.**
- 기호(Unicode `So`) 총 576회 / 226만 자. 청크 기준 248개(4.6%)에 포함.
  상위는 `▼`(182) `✔`(96) `✓`(44) `👉`(28) `🔺`(25). 대부분 유형 G의
  링크 유도 장식이라 보일러플레이트로 잡는 게 맞고, 인코딩 문제는 아니다.
- 자모 반복(`ㅋㅋ`/`ㅠㅠ`) 포함 청크 199개(3.7%). 손상이 아니라 문체다.
- **서로 다른 문서에서 동일 텍스트가 나온 청크 0개** → `chunk_id` 충돌 없음.
  다만 이건 breadcrumb에 문서 제목이 들어가서 그런 것이고, 본문만 놓고 보면
  중복이 없다는 뜻은 아니다.

## 3. 판정 — 이 로직을 829건에 그대로 적용해도 되는가

### 아니다. 지금 상태로는 넣으면 안 된다.

크래시가 없으므로 실행은 된다. 그래서 더 위험하다 — 실패가 로그에 안 남고
코퍼스 안에서만 보인다.

**근거 (확신 있는 것)**

1. **보일러플레이트가 코퍼스의 3분의 1에 들어간다.** 청크 1,793개(33.3%),
   도입 청크의 33.4%. 크롤러 메타(`훈련/케어/질병 ○○○ 애견훈련소장
   2018. 12. 14. 23:50`)와 링크 유도 문구가 본문 텍스트로 임베딩된다.
   같은 필자의 529개 문서에 같은 문자열이 반복되므로, 이건 노이즈가 아니라
   **529개 벡터를 서로 끌어당기는 공통 성분**이다. 최근 Q&A breadcrumb 사고와
   같은 구조이고, 규모는 훨씬 크다.
2. **헤딩 승격은 이 원자재에서 신뢰할 수 없다.** 승격 경로를 탄 58건 중 57건에
   오승격이 있고, 승격 헤딩 467개 중 304개(65%)가 문장 조각이다. 문장 한복판이
   섹션 경계가 되면서 `입니다.` 한 줄짜리 청크와 breadcrumb이 91%인 청크를
   만든다. 헤딩 경로 청크의 39.6%가 최소 길이 미달이다.
3. **규모가 검증 비율을 뒤집는다.** 문서 코퍼스 219청크 → 5,389청크.
   사람이 구조를 확인한 문서에서 나온 청크 비중이 100%에서 4%로 떨어진다.
   `chunking_method`로 필터백이 가능하다는 설계 의도가 있지만, 필터하고 나면
   남는 게 4%라면 그건 필터가 아니라 코퍼스가 바뀐 것이다.
4. **`blog_raw_rescue` 103건은 소스 다양성을 늘리지 않는다.** 기존 두 블로그의
   다른 글이다. 넣으면 이미 지배적인 두 필자의 비중이 더 커진다.

**애매하다고 써야 할 것**

- **문장 중간 절단률**을 결함으로 셀지가 애매하다. 관대 기준 62.5%는 현행
  코퍼스(PDF 제외) 25%의 2.5배지만, 그 차이의 대부분은 "하드랩 폴백 경로가
  9.6%에서 92.5%로 늘어나서"이지 "로직이 새로 고장나서"가 아니다. 같은 경로만
  비교하면 현행 76.2% vs dry-run 65.1%로 오히려 dry-run 쪽이 낫다(현행 n=21로
  표본이 작다). 반면 헤딩 경로의 5.6% → 31.2%는 새 결함이 맞다.
- **검색 품질에 실제로 얼마나 나쁜지는 측정하지 않았다.** 이 작업은 파싱
  산출물만 봤다. 위 수치들은 "임베딩이 오염될 것으로 보이는 구조"이지
  Hit@1/MRR 하락의 실측이 아니다. gold 셋 확장이 끝난 뒤 소규모(예: 50건)로
  실제 검색 지표를 재보기 전에는 "얼마나" 나쁜지 단정할 수 없다.
- **단어 중간 분할 48~68회**는 사전 없이 코퍼스 통계로 센 추정이다. 놓친 것도
  오탐도 있다. 다만 문서 대비 5% 수준이라 우선순위를 좌우하지는 않는다.
- **핏펫 8건은 이 판정에서 빼도 된다.** 헤딩 승격이 정상 작동하고(이상 21%),
  보일러플레이트 2건, 절단 7.8%로 세 지표 모두 네이버 두 소스와 다르다.
  표본이 8건뿐이라 단정은 못 하지만, "generic 웹 소스는 다르게 취급해야 한다"는
  방향은 데이터가 지지한다.

## 4. 고쳐야 할 것 — 우선순위와 예상 영향 범위

**아무것도 고치지 않았다.** 아래는 제안이고, 승인 전에는 손대지 않는다.

`chunk_id`는 청크 텍스트의 SHA-256이다. **텍스트를 바꾸는 수정은 전부 기존
청크의 id를 바꾼다** → 해당 문서 재인제스트 + 임베딩 재생성이 따라온다.
gold 셋 확장이 진행 중이므로 이 점이 우선순위를 결정한다.

### P1 — `clean()`의 보일러플레이트 규칙 확장

무엇: 네이버 메타 줄(`YYYY. M. D. HH:MM` 패턴), 카테고리 라벨, `애견훈련소장`
서명, `바로가기`/`아래링크는` 링크 유도, 그리고 **하드랩으로 쪼개진 서명**
(줄 결합 후 매칭하거나 `입니다.` 단독 줄 처리).

- 효과: 청크 1,793개(33.3%)에서 공통 성분 제거. 도입 청크 오염 33.4% → 대폭 감소.
- 영향 범위: `clean()`만 수정. 기존 17문서 중 네이버 크롤 3건
  (`berrardog-patella`, `berrardog-separation-anxiety`, `africaamc-night-barking`)의
  텍스트가 바뀔 가능성이 있다 → **그 3건의 chunk_id 변경, 임베딩 재생성 필요.**
  나머지 14건(수동/easiestip/핏펫/PDF)은 해당 문자열이 없어 영향 없을 것으로
  보이지만 재확인이 필요하다.
- 위험: 낮음. 삭제 후보가 전부 조언이 아닌 furniture다. 다만 `그렇기때문에`
  (125문서)처럼 **본문 접속어인데 반복 빈도가 높은 줄**은 지우면 안 된다.
  빈도만으로 자동 삭제하면 안 되고 목록을 사람이 확정해야 한다.

### P2 — 대량 인제스트를 소스별 화이트리스트로 제한

무엇: 829건 일괄이 아니라, 헤딩 승격이 실제로 작동하는 소스(핏펫형 generic 웹)와
작동하지 않는 소스(네이버 블로그)를 나눠 다르게 처리. 네이버 두 소스는
승격을 아예 끄고 폴백 고정.

- 효과: 유형 A(오승격 304개)가 사라진다. 헤딩 경로 청크 404개 중 네이버
  분(322개)이 폴백으로 이동 → 최소 길이 미달 160개 대부분 해소.
- 영향 범위: `ingest_documents.py`의 진입점만. **기존 코퍼스 무변경.**
  기존 MANIFEST의 네이버 크롤 3건은 이미 하드랩 판정으로 폴백을 타고 있어
  결과가 같다.
- 위험: 낮음. 다만 "네이버는 구조를 못 쓴다"를 받아들이는 결정이므로,
  `heading_path` 기반 parent-child 리트리버 계획은 이 소스에서 포기하는 셈이다.

### P3 — `is_hard_wrapped()` 임계 조정 (AND → 완화)

무엇: `short_share >= 0.85 AND median <= 30`이 0.80~0.85 구간을 놓친다.
OR로 바꾸거나 임계를 0.65 근처로 낮춘다.

- 효과: 유형 C 32건이 폴백으로 이동. P2를 하면 네이버 분은 자동 해결되므로
  **P2의 부분집합**이다. P2를 채택하면 P3는 generic 웹 소스에만 의미가 있다.
- 영향 범위: **여기가 기존 코퍼스를 건드린다.** 임계를 0.60/34로 낮추면
  현행 MANIFEST의 `yd-otitis-externa`(short_share 0.68, median 27, 승격 14개)가
  하드랩으로 뒤집혀 헤딩을 전부 잃는다. 이 문서는 사람이 확인한 수동 문서다.
  → **현행 219청크 중 해당 문서 몫이 재청크된다.**
- 위험: 중간. P2로 대체 가능하면 굳이 이걸 먼저 할 이유가 없다.

### P4 — 승격 헤딩 후처리 검증

무엇: 승격 직후 조사/연결어미 종결, 3자 이하, 직전 줄 미완결을 거부.

- 효과: P2를 안 하고 승격을 유지할 경우의 차선책. 304개 중 상당수를 걸러낸다.
- 영향 범위: `promote_headings()` 수정. 기존 헤딩 경로 문서
  (`yd-patella`, `yd-otitis`, `salgoonews`, 핏펫 2건)의 승격 결과가 바뀔 수 있다
  → 최대 54청크 재생성.
- 위험: 중간. P2를 채택하면 불필요하다. **P2와 P4는 택일이다.**

### P5 — 넣기 전에 소규모 실측

무엇: 829건 전량이 아니라 P1 적용 후 50~100건만 인제스트해서 기존 gold 셋으로
Hit@1/MRR 비교. 3절에서 "측정 안 했다"고 쓴 부분을 메우는 단계.

- 영향 범위: gold 셋 확장이 끝난 뒤에 해야 한다. 지금 하면 다른 세션 작업과
  충돌한다.

### 하지 말아야 할 것

- `blog_raw_rescue` 103건을 "새 소스"로 계산하지 말 것 (기존 두 블로그의 다른 글).
- 반복 줄을 빈도만 보고 자동 삭제하지 말 것 (`그렇기때문에` 같은 본문 접속어가
  상위에 있다).
- gold 셋 확장이 끝나기 전에 임베딩 인덱스를 다시 만들지 말 것.
