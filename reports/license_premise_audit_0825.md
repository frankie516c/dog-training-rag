## 4. 판단하지 않은 것

- **어떤 조치가 필요한지 정하지 않았습니다.** 이력 재작성(force push)은
  아카이브 브랜치 9개를 포함해 원격 이력 전체를 건드리는 일이고, 되돌릴 수
  없습니다. 승인 없이 손댈 종류의 작업이 아닙니다.
- 저장소를 private으로 되돌리는 것과 커밋된 원문을 제거하는 것 중 무엇이
  맞는지도 판단하지 않았습니다. 전자는 한 번의 설정 변경이고 후자는 이력
  재작성입니다. 선택지의 성격이 다릅니다.
- 공정이용 성립 여부는 법적 판단이라 하지 않았습니다. 위 표는 문서가 스스로
  적어둔 기준과 현재 상태의 대조일 뿐입니다.

## 6. `combined_v4_e5_metrics.json`의 텍스트 필드 — 불필요, 스키마에서 제거함

### 확인 결과: 회귀 검증에 필요 없습니다

근거 네 가지입니다.

1. **읽는 코드가 없습니다.** `top_k[].text`를 커밋된 metrics 파일에서 되읽는
   스크립트·테스트가 하나도 없습니다. metrics를 로드하는 4개 스크립트
   (`analyse_refusal_signals`·`analyse_score_gap`·`diagnose_synthetic_misses`·
   `probe_out_of_corpus`)는 전부 **코퍼스에서** `text`를 읽지 metrics에서 읽지
   않습니다.
2. **다른 스냅샷 6개는 애초에 `text`가 없습니다.** `data/eval/results/`의
   `*_metrics.json` 7개 중 텍스트 필드를 가진 것은 `combined_v4` 하나뿐입니다.
   나머지는 `evaluate_youtube_retrieval.py`가 만들었고 `text`를 쓰지 않습니다.
   **청크 크기를 v3로 확정한 v1↔v3 비교가 바로 그 텍스트 없는 스냅샷들로
   수행됐습니다**(`chunking_config.py` 독스트링). 회귀 검증에 본문이 필요했다면
   그 비교가 불가능했어야 합니다.
3. **식별에 필요한 것은 남습니다.** `chunk_id`·`rank`·`score`·게이트 판정·
   `first_relevant_rank`·`reciprocal_rank`가 그대로입니다. `where`는 이미
   사람이 읽는 이름을 담고 있습니다(`문서 · 슬개골 탈구 단계별 증상`).
4. **`.md` 리포트는 영향 없습니다.** 리포트는 파일이 아니라 메모리상의 payload에서
   생성되므로 150자 스니펫을 그대로 출력합니다.

### 실제 비용 — 있습니다

`.gitignore` 주석이 이 예외를 둔 이유는 "코퍼스를 다시 만들면 되살릴 수 없다"
입니다. 본문을 빼면 **코퍼스가 재생성돼 `chunk_id`가 바뀐 뒤에는 옛 스냅샷의
`chunk_id`를 실제 텍스트로 되짚을 수 없습니다.** 이건 실재하는 손실입니다.

다만 그 손실은 다른 6개 스냅샷이 이미 감수하고 있는 것과 같은 종류이고,
`where`·`slot`·`chapter_title`이 남으므로 "어떤 성격의 청크가 몇 위였나"는
읽힙니다. 본문 전체를 공개 저장소에 남기는 대가로 살 만한 값은 아니라고
판단했습니다.

`scripts/run_combined_retrieval_eval.py`에 `without_chunk_text()`를 추가하고
JSON 직렬화 직전에만 적용했습니다. 리포트 생성은 그대로입니다. 테스트 3개 추가,

**이건 앞으로 생성될 스냅샷에만 적용됩니다. 이미 커밋된 8개 버전은 그대로

## 8. "고쳐서 새로 커밋"으로는 끝나지 않습니다

**이것이 이 리포트의 핵심입니다.**

6절의 스키마 수정도, 파일을 지우는 커밋도, **과거 커밋의 내용을 바꾸지
않습니다.** git 커밋은 불변이고, 지우는 커밋은 "지웠다는 사실"을 이력에 한 줄 더
추가할 뿐입니다. `combined_v4_e5_metrics.json`의 8개 버전은
`git show <sha>:data/eval/results/combined_v4_e5_metrics.json` 한 줄로 지금도
전부 꺼낼 수 있고, GitHub에서는 커밋 URL로 브라우저에서도 열립니다.

**이력에서 실제로 제거하려면 `git filter-repo` 또는 BFG로 이력을 재작성하고
force push 해야 합니다. 다른 방법이 없습니다.**

### 이력 재작성을 할 경우와 안 할 경우

| | 안 할 경우 | 할 경우 (filter-repo + force push) |
|---|---|---|
| 과거 커밋의 원문 | 그대로 접근 가능 | ref에서 도달 불가 |
| 커밋 해시 | 유지 | **전부 변경** — 17개 원격 브랜치 + 태그 `vector-baseline-v3` |
| 다른 로컬 클론 | 영향 없음 | 재클론 필요 (이 PC에 최소 2개: `-retrieval`, `-collision-dogs`) |
| 진행 중인 gold 작업 | 영향 없음 | **다른 세션의 브랜치가 깨집니다** |
| 이미 받아간 사본 | 회수 불가 | **회수 불가 (동일)** |
| GitHub 서버의 dangling 객체 | 남음 | **남을 수 있음** — 아래 |

### force push 후에도 남는 것 (일반적인 GitHub 동작, 이 저장소에서 검증한 것 아님)

- force push로 참조가 끊긴 커밋은 GitHub 저장소에 **dangling 상태로 남고, SHA를
  아는 사람은 `github.com/…/commit/<sha>`로 계속 열 수 있습니다.** GitHub는
  즉시 GC하지 않습니다. 확실히 지우려면 **GitHub Support에 GC를 요청**해야
  한다는 것이 GitHub 자신의 안내입니다.
- fork가 있으면 객체가 fork 네트워크에 남아 원본을 지워도 접근 가능합니다.
  **이 저장소는 fork 0개라 이 경로는 없습니다** (아래 실측).
- GitHub 코드 검색 인덱스는 재크롤 전까지 삭제된 내용을 들고 있을 수 있습니다.
- **Software Heritage·GHArchive 같은 제3자 아카이브의 수집 여부는 확인하지
  못했습니다.** 외부 조회가 필요합니다. 원하시면 확인하겠습니다.

### 이 저장소의 실측 노출 지표 (GitHub API, 2026-08-25)

| 항목 | 값 |
|---|---|
| 공개 여부 | **PUBLIC** (생성 2026-08-12) |
| fork | **0** |
| star / watcher | 0 / 0 |
| clone (14일) | **129회 / 고유 85** |
| view (14일) | 119회 / **고유 6** |

읽는 법에 주의가 필요합니다.

- **clone 85 고유 vs view 고유 6.** 사람이 저장소를 보고 클론하는 패턴이면 view가
  clone보다 많거나 비슷합니다. 반대로 나온 것은 **자동화 클라이언트**(CI, 봇,
  코드 스캐닝 크롤러, 또는 이 PC의 도구가 매번 새 클론을 만드는 경우)의 서명에
  가깝습니다. 이 PC에만 로컬 클론이 최소 2개 있습니다.
- **GitHub 트래픽 API는 "누가" 클론했는지 알려주지 않습니다.** 85건 중 몇 건이
  제3자인지 이 데이터로는 판별할 수 없습니다. "제3자 사본이 있다"고도
  "없다"고도 단정하면 안 됩니다.
- 일별로는 8/13~8/14에 몰려 있습니다(16 + 37회). 그 시점에 무엇을 했는지는
  이 데이터 밖입니다.

### private 전환은 무엇을 해결하는가

- **해결합니다**: 익명 접근이 전부 막힙니다. tip뿐 아니라 **dangling 커밋도
  SHA를 알아도 인증 없이는 못 엽니다.** 코드 검색 인덱스에서도 빠집니다.
  fork가 0이라 "fork가 public으로 떨어져 나가는" 문제도 없습니다.
- **해결하지 않습니다**: 이미 클론된 사본, 제3자 아카이브의 스냅샷, 캐시된
  검색 결과. 이건 이력 재작성으로도 해결되지 않는 것과 **같은 집합**입니다.
- **성격이 다릅니다**: private 전환은 설정 한 번이고 되돌릴 수 있으며 진행 중인
  다른 세션 작업에 영향이 없습니다. 이력 재작성은 되돌릴 수 없고 17개 브랜치의
  해시를 전부 바꿉니다.

정리하면 — **지금 계속되는 공개 노출을 멈추는 것은 private 전환이 하고, 이력에서
원문 자체를 없애는 것은 재작성이 합니다. 이미 나간 사본은 둘 다 못 되돌립니다.**
둘은 배타적이지 않고, 순서를 정할 수 있는 별개의 조치입니다.

**결정은 하지 않았고 아무 조치도 취하지 않았습니다.** 이력 재작성은 지시대로
진행하지 않았습니다.
